# Project files vs lore — what goes where

Project files I own, such as my workspace layer, local-only instruction files
and my own records for a project, hold what is specific to it: this team's
quirks, this repository's conventions, ongoing initiatives, how this project's
tracker behaves. They load only when working in that project.

Lore (this knowledge base) holds what is portable: durable, cross-project
engineering knowledge that follows me anywhere.

Before adding a rule to a project file I own, search lore for overlap. If lore
already covers it, don't repeat it. If it is portable but not yet in lore, put
it in lore, worded without the project's specifics, and keep only what is
genuinely local in the project. Never keep the same rule in both places; the
copies drift and dilute lore as the source of truth.

Files the team owns, such as checked-in instruction files, keep their rules
whatever lore holds, because teammates don't load lore. Lore may take a generic
version of such a rule, never the client's specifics.

Report findings before moving or removing a rule; don't act unilaterally.
